# 시연 시나리오 — 페르소나 · as_of 고정값

> 작성: 2026-08-12 · 근거: `main`(정책 5건 + 규칙 엔진) 실측
> 아래 숫자는 전부 실행 결과다. 추정값이 아니다. 재현 방법은 마지막 절.

---

## ⚠️ 먼저 — 발표일에 `as_of` 를 고정하지 않으면 화면이 빈다

정책 5건의 마감일 분포가 이렇다.

| policy_id | 정책 | 마감 |
|---|---|---|
| hs-2026-0263 | 청년 부동산 중개보수·이사비 | 2026-03-06 **(종료)** |
| hs-2026-2673 | 청년 내:일(job)응원금 2차 | **2026-08-14** |
| hs-2026-2594 | 청년 전(월)세 대출이자 | **2026-08-14** |
| hs-2026-0000 | 노인 보청기 | 상시 |
| hs-2026-0001 | 성인용 보행기 | 상시 |

**청년 정책 3건이 모두 8/14 이전에 마감된다.** 분류 규칙 0(마감 종료 제외)에 의해 8/15부터는
응답에서 통째로 빠진다. **발표일은 8/20 이라 이미 전부 지난 뒤다.** 실측:

```
청년 페르소나 · as_of 2026-08-20 (발표일)
  → eligible 0 / docs_needed 0 / upcoming 0      ← 화면이 완전히 빈다
```

### 대응

1. **시연은 반드시 `as_of` 를 고정한다** — 아래 페르소나의 고정값을 그대로 쓴다.
   계약서가 `as_of` 를 선택 필드로 넣어둔 이유가 정확히 이것이다(시연 재현성).
2. 근본 해결은 **마감이 8/20 이후인 정책 확보**다 → #10(크롤러) · #24(초안 14건 검수)

## 페르소나 A — 청년 전입자 (D-day 시연)

```json
{
  "birth_date": "1999-03-02",
  "region": "화성시 동탄5동",
  "move_in_date": "2026-02-01",
  "lifecycle": ["전입", "청년"],
  "household_type": "1인가구",
  "as_of": "2026-06-01"
}
```

**결과 — `eligible` 0 / `docs_needed` 1 / `upcoming` 1**

| 분류 | 정책 | 내용 |
|---|---|---|
| docs_needed | hs-2026-2594 청년 전월세 대출이자 | 기계 조건 통과, 소득·서술형 확인 남음 |
| **upcoming** | hs-2026-2673 청년 내:일응원금 | **D-61 (2026-08-01 충족)** — 거주 6개월 요건 |

`as_of` 를 **2026-06-01 로 고정해야 한다.** 오늘 날짜로 돌리면 거주 6개월 충족일(8/1)이
마감(8/14)을 넘지는 않지만 이미 지나 `docs_needed` 로 바뀌고, 8/15 이후엔 아예 사라진다.

### 이 페르소나가 보여주는 것

- **시간축** — "당신은 8월 1일부터 신청할 수 있습니다" (복지로에는 없는 정보)
- **`upcoming` 에 실린 `verify`** — 거주 요건이 충족돼도 소득 서류 확인이 남는다는 안내
  → 화면 문구 "미리 준비하세요" 의 근거 데이터

## 페르소나 B — 노인 전입자 (상시 접수 + D-day)

```json
{
  "birth_date": "1955-05-05",
  "region": "화성시 봉담읍",
  "move_in_date": "2025-09-01",
  "lifecycle": ["노후"],
  "household_type": "1인가구",
  "as_of": "2026-08-11"
}
```

**결과 — `eligible` 0 / `docs_needed` 0 / `upcoming` 2**

| 분류 | 정책 | 내용 |
|---|---|---|
| upcoming | hs-2026-0000 노인 보청기 | **D-21 (2026-09-01 충족)** — 거주 12개월 요건 |
| upcoming | hs-2026-0001 성인용 보행기 | **D-21 (2026-09-01 충족)** — 거주 12개월 요건 |

이 페르소나는 **상시 접수(`deadline: null`) 정책**이라 마감 절벽의 영향을 받지 않는다.
발표일 당일(`as_of` 2026-08-20)에도 `upcoming` 2건이 **D-12** 로 정상 표시된다 — 실측 확인.

`as_of` 고정 없이도 동작하는 유일한 페르소나이므로, **라이브 시연의 안전판**으로 쓸 수 있다.

### 이 페르소나가 보여주는 것

- **생애주기 축 확장** — 청년 일변도가 아님을 보여준다
- **상시 접수 처리** — 마감 자리에 "상시" 표시 (규칙 0·2의 마감 비교 건너뜀)

## 페르소나 C — 미확보 ⚠️

**`eligible`(확정 대상)에 도달하는 정책이 현재 0건**이라, 3분류 중 한 칸을 채우는 페르소나를
만들 수 없다.

원인은 구조적이다 — `manual_conditions`(서술형 자격요건)가 하나라도 있으면 최고 분류가
`docs_needed` 다. 현재 5건 전부 서술형 조건을 가지고 있다.

| policy_id | manual_conditions |
|---|:---:|
| hs-2026-0263 | 14 |
| hs-2026-2594 | 11 |
| hs-2026-2673 | 6 |
| hs-2026-0000 | 3 |
| hs-2026-0001 | 2 |

→ **#8** 에서 다룬다. 서술형 조건이 없는 단순 지원사업 1건을 확보하면 해결된다.

### 그때까지의 발표 대응

"확정 대상" 칸이 비는 것을 **약점이 아니라 설계 결과로 설명**할 수 있다.

> 실제 공고의 자격요건은 대부분 서류 확인이 필요합니다.
> 저희는 확인이 필요한 항목을 임의로 통과시키지 않고 '서류 확인 필요'로 분류합니다.
> 자격이 없는 분께 "대상입니다"라고 말하지 않기 위해서입니다.

## 재현 방법

```bash
cd apps/api
pip install -r requirements.txt
python - <<'PY'
from datetime import date
from app.store import load_policies
from app.schemas import Profile
from app.engine.evaluate import evaluate_all

P = load_policies()
prof = Profile(
    birth_date=date(1999, 3, 2), region="화성시 동탄5동",
    move_in_date=date(2026, 2, 1), lifecycle=["전입", "청년"],
    household_type="1인가구",
)
r = evaluate_all(prof, P.values(), date(2026, 6, 1))
for k in ("eligible", "docs_needed", "upcoming"):
    print(k, [i["policy"]["policy_id"] for i in r[k]])
PY
```

API 로 확인하려면 위 JSON 을 그대로 `POST /evaluate` 에 보내면 된다 (`as_of` 포함).
